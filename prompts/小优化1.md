## 🛠️ 优化 1：调度事件驱动化（去除数据库轮询）
### 背景
当前 Scheduler 每秒扫描 `status=CREATED` 节点，导致 1s 延迟和 DB 压力。改为事件驱动 + 30s 兜底扫描。

### 改动点
1. **修改 `internal/orchestrator/scheduler.go`**
   - 移除每秒全表扫描，改为 30s 一次兜底扫描
   - 兜底仅处理 `CREATED` 且 `updated_at < NOW() - 1 MINUTE` 的节点
   - 兜底扫描时打印 Warn 日志

2. **增强 `internal/orchestrator/state_service.go`**
   - 节点状态变为 `CREATED` 后，立即调用 `DependencyChecker.TryMakeReady()`

3. **调整 `internal/orchestrator/retry.go`**
   - 节点重试回退到 `CREATED` 后，同样调用 `TryMakeReady()`

### 验证
- 日志无每秒扫描记录
- 任务执行延迟降至毫秒级

## 🛠️ 优化 2：Worker 安全加固（Bash 工具防护）
### 背景
Bash 工具直接执行 Shell 命令，存在注入风险。先做最小化加固。

### 改动点
1. **增强 `internal/worker/tools/bash.go`**
   - 添加命令白名单（`ls`, `cat`, `echo`, `curl`, `python`, `node` 等）
   - 过滤危险字符（`;`, `|`, `&&`, `||`, `` ` ``, `$()`, `>`, `<`）
   - 限定工作目录为 `/tmp/ai-sandbox`
   - 添加默认 30s 超时（`context.WithTimeout`）

### 验证
- 含管道/分号的命令被拒绝
- 未在白名单的命令被拒绝
- 正常命令可成功执行

## 🛠️ 优化 3：DAG 增加条件分支支持
### 背景
支持 LLM 根据上游输出动态决定后续流程。

### 改动点
1. **数据库迁移**
   ```sql
   ALTER TABLE ai_node ADD COLUMN IF NOT EXISTS condition TEXT;
   ```

2. **扩展 `internal/model/ai_node.go`**
   - 添加 `Condition string` 字段

3. **修改 `internal/orchestrator/dependency_checker.go`**
   - 上游成功后，若节点有 `condition` 则评估
   - 条件为假时，节点状态变为 `SKIPPED`（新增状态）
   - `SKIPPED` 视为完成，满足下游依赖

4. **新增状态常量**
   - `NodeStatusSkipped = "SKIPPED"`

### 验证
- 节点 B 条件设为 `A.output.status == "success"`
- A 成功则 B 执行，A 失败则 B 跳过，下游仍正常执行

## 🛠️ 优化 4：引入发件箱模式（Outbox Pattern）
### 背景
先写 DB 再发 Kafka，若 Kafka 失败则事件丢失。改为同一事务写 DB + outbox，再由 relay 转发。

### 改动点
1. **新建 outbox 表**
   ```sql
   CREATE TABLE IF NOT EXISTS outbox (
       id BIGSERIAL PRIMARY KEY,
       aggregate_type VARCHAR(50) NOT NULL,
       aggregate_id VARCHAR(100) NOT NULL,
       event_type VARCHAR(100) NOT NULL,
       payload JSONB NOT NULL,
       created_at TIMESTAMPTZ DEFAULT NOW()
   );
   CREATE INDEX IF NOT EXISTS idx_outbox_created ON outbox(created_at);
   ```

2. **修改 StateService**
   - 不再直接发 Kafka，而是将事件写入 outbox，与业务更新在同一事务

3. **创建 Outbox Relay**
   - 新建 `internal/outbox/relay.go`
   - 每 100ms 从 outbox 按顺序读取记录，发送到 Kafka，成功后删除

### 验证
- 手动停止 Kafka，任务状态仍正常流转，事件写入 outbox
- Kafka 恢复后，事件被正常发送，Worker 消费无误
