# 标书章节清单一致性设计

## 背景

批量生成章节时，九份 Markdown 初稿已写入 `outputDir/章节/`，但项目清单只保留了第 1、2、7、9 章；其中第 7 章被登记两次。章节工作区只读取项目清单并按章节号聚合版本，因此页面显示四章而非目录中的九章。

根因是前端在同一循环中发起多个异步单章登记请求，而本地代理的单章登记使用“读取 `project.json`、修改内存对象、写回 `project.json`”的读改写流程，未对同一项目串行化。并发请求会以陈旧快照覆盖彼此的写入。

## 目标

1. 让一次批量章节生成以原子方式登记所有成功章节，后续刷新、重启和重新打开项目都能看到完整章节列表。
2. 让单章登记与批量登记在并发调用时不丢失项目清单产物。
3. 自动从当前项目的章节目录恢复已生成但未登记的初稿和扩写稿，并清理同一源文件的伪重复记录。
4. 保留现有 Markdown 文件的内容、路径和修改时间；本设计不重新生成、不覆盖、不删除用户章节文件。

## 非目标

- 不改动云端章节生成模型、提示词或章节正文质量逻辑。
- 不通过文件名不匹配的任意 Markdown 文件推断章节；无法可靠识别的文件只报告，不自动纳入项目。
- 不改变普通项目读取接口的无副作用语义。

## 方案比较

### 方案 A：仅前端顺序登记

前端逐个等待单章登记完成。该方案改动少，但任何其他调用方仍可同时触发本地代理的读改写竞争，并且九章生成需要九次清单写入，不采用。

### 方案 B：仅后端项目级互斥锁

后端为同一项目的单章登记串行化。数据不会丢失，但批量生成仍会产生多次 HTTP 请求、多次磁盘写入和多次前端状态更新，不采用为主路径。

### 方案 C：批量原子登记 + 后端项目级互斥锁 + 目录对账（采用）

前端将一批成功章节作为一个请求提交。本地代理在项目级互斥锁内将整批章节合并到清单并只写一次。既有单章登记也使用同一锁，供扩写和兼容调用使用。独立的目录对账端点为历史项目补回遗漏记录，并可安全重复调用。

## 架构与数据流

```text
章节生成成功结果（N 章）
  -> 前端规范化每章的稳定身份与 metadata
  -> POST /api/local/biaoshu/projects/:id/artifacts/batch
  -> 本地代理取得该项目互斥锁
  -> 一次读取 project.json，校验并合并 N 条产物，一次写回
  -> 返回完整项目清单
  -> 前端以该响应刷新 activeProject 与章节工作区

项目打开后发现章节目录与清单不一致
  -> POST /api/local/biaoshu/projects/:id/artifacts/reconcile-chapters
  -> 同一项目互斥锁
  -> 解析任务书、扫描章节目录、补回缺失记录、折叠伪重复
  -> 返回对账统计与完整项目清单
```

## 后端设计

### 项目级写入协调

`Server` 持有按 `projectID` 索引的互斥锁注册表。以下操作必须取得同一项目的锁，并覆盖完整的“读清单、合并、写清单、重新读取返回”生命周期：

- 现有单条产物登记；
- 新增批量产物登记；
- 新增章节目录对账。

锁注册表只在本地代理进程内协调 HTTP 请求；清单写入继续沿用已有 JSON 写入机制。所有合并均以磁盘中锁内读取到的最新清单为基准，而不使用调用方携带的旧清单。

### 批量登记接口

新增 `POST /api/local/biaoshu/projects/:projectId/artifacts/batch`。

请求体为 `artifacts: BiaoshuArtifactRegisterRequest[]`。服务端在写入前校验：

- 数组不能为空；
- 每项必须有 `kind`、`storageRef` 和可解析的稳定 `id`；
- 同一请求中的 `id` 不得重复；
- `storageRef` 必须位于当前项目的 `outputDir` 内；
- 章节产物必须具有正整数 `metadata.chapterNumber`。

任何一项校验失败时返回 400，且不写入清单。校验通过后按 ID 执行 upsert，一次写入 `project.json` 与输出目录镜像，并返回完整 `project`。

### 章节目录对账接口

新增 `POST /api/local/biaoshu/projects/:projectId/artifacts/reconcile-chapters`，返回：

- `project`：对账后的完整清单；
- `added`：补回的初稿或扩写稿 ID；
- `deduplicated`：移除的伪重复清单 ID；
- `unclassified`：未被安全识别、未写入清单的文件名；
- `changed`：是否发生清单写入。

对账逻辑限定在 `<outputDir>/章节/` 的直接文件：

- `NN_<标题>_初稿.md` 生成稳定 ID `chapter-NN`，`draftStage=initial`；
- `NN_<标题>_扩写稿.md` 生成稳定 ID `chapter-NN-expanded`，`draftStage=expanded`；
- 其他文件列入 `unclassified`，不改变清单。

服务读取同目录上级的 `04_章节写作任务书.md`，提取每个 `### 第…章` 区块的标题与 `estimatedWordCount`。恢复记录的 `targetWords` 来自该任务书，`wordCount` 按现有章节字数统计规则计算。任务书缺失或个别章节不可解析时，仍可登记文件路径和章节号，但在响应中报告该章节缺少目标字数。

当清单中同一 `storageRef`、同一章节号、同一 `draftStage` 存在多条记录时，保留 `updatedAt` 较新且元数据较完整的一条，将其规范为稳定 ID；其余记录从清单移除。文件不被删除。对账操作可重复执行：第二次执行不新增、不去重、不改写。

## 前端设计

### 批量章节生成后的登记

章节生成成功后，前端仍立即更新本次会话中的章节提示，但不再调用会自行发起异步单条登记的通用回调。前端先将所有无错误的生成结果转换为章节产物，再调用批量登记接口一次。

批量响应返回后，前端一次性更新 `activeProject`、项目历史和工作区数据。批量请求失败时，保留生成结果和文件路径，向用户显示“初稿文件已生成但项目登记失败”的可操作错误，并提供对账入口；不得声称生成失败。

### 自动恢复历史项目

打开已管理项目后，前端根据清单中 `BID_CHAPTER_TASK_BOOK`、章节目录与 `BID_CHAPTERS` 记录进行一次低成本差异检查。仅当发现章节文件数量、章节号集合或重复源文件不一致时，调用对账端点；正常项目不产生额外写入。

对账响应发生变化时，工作区显示“已恢复 N 章、已清理 N 条重复记录”。存在 `unclassified` 或缺失目标字数时显示非阻塞警告，用户可继续查看已恢复章节。

## 兼容性与安全约束

- 现有单条 `POST /artifacts` 路由保持可用；扩写流程无需变更调用协议。
- 所有章节路径验证必须使用清理后的绝对路径，且必须位于项目 `outputDir` 下。
- 只接受 `.md` 文件；不通过内容执行、导入或修改任何文件。
- 目录对账仅更新项目清单和镜像清单，绝不写入章节正文。
- 工作区按 `chapterNumber` 聚合版本的现有行为保持不变；恢复后第 7 章只保留真实初稿或真实扩写版本。

## 验收标准

1. 对当前“养护”项目执行对账后，清单包含第 1 至第 9 章共九个初稿章节，第 7 章不再因同一初稿文件显示为两个版本。
2. 九章批量生成后，无论网络响应顺序如何，重新加载项目均显示九章。
3. 以并发方式登记九个不同章节，最终清单必须含九个唯一章节，且不丢失已有非章节产物。
4. 对账重复执行不会改变清单或重复生成事件。
5. 文件名不符合规则的 Markdown 不进入工作区，并在响应中被报告。
6. 本地后端单元与竞态检测、前端章节逻辑测试和生产构建均通过。
