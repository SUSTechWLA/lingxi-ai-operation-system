## 2. 架构设计

### 2.1 核心思路

**不是解析任务书 → 而是把任务书作为整体上下文，让 LLM 按索引生成指定章节。**

理由：任务书是 LLM 生成的 markdown，格式可能有差异。直接解析其结构脆弱。更好的方式是把任务书全文作为 system/context 传给 LLM，然后指示 LLM "请写第 N 章"。

### 2.2 请求流程

```
前端 (BiaoshuWorkbench)
  ↓ POST /api/biaoshu/chapters/generate
  ↓ { taskBookPath, outlinePath, scoringReportPath, analysisReportPath, contextReportPath, outputDir }
  ↓
Handler (chapter_generation_handler.go)
  ↓ 参数校验 → 调用 service
  ↓
Service (chapter_generation_service.go)
  ├── 1. 读所有输入文件
  ├── 2. 解析大纲获取章节列表（从 markdown 标题提取）
  ├── 3. 对每个章节并发调用 LLM（semaphore 限制 3 并发）
  │      ├── System Prompt：写作规则（格式、词汇、结构约束）
  │      └── User Prompt：任务书全文 + 该章大纲 + 评分标准 + 项目背景
  ├── 4. 每个章节写入 章节/{序号}_{章节名}_初稿.md
  └── 5. 返回 [{ chapterNumber, chapterTitle, filePath, content, artifact }, ...]
  ↓
前端
  ├── 逐章注册为 BID_CHAPTERS artifact
  └── 刷新产物列表
```

### 2.3 章节列表提取

不从任务书提取，**从大纲提取**。大纲是 `03_技术标四级大纲.md`，一级标题格式如：

```markdown
## 一、总体项目管理方案
## 二、施工方案
## 三、...
```

通过正则 `^##\s*[一二三四五六七八九十]+、.+` 提取一级标题作为章节列表。outline 服务已明确规定 `## 一级标题（章节）` 格式，且中文序号特征可防误匹配 `### 二级标题`。

这比解析任务书更可靠。

#### 3.2.3 字数按评分权重分配

**原则**：每章目标字数 = 总目标字数 × (该章评分分值 / 总评分分值)。

```go
// 伪代码流程
func calculateChapterWordCounts(
    scoringContent string,  // 评分标准拆解表
    taskBookContent string, // 章节写作任务书
    totalWordCount int,     // 总目标字数（从任务书"总字数预估"提取，默认 50000）
) (map[int]int, int, error) {

    // 1. 从评分标准拆解表提取总评分分值
    totalScore := extractTotalScoreFromScoring(scoringContent)
    // 正则匹配 "总分" 或 "合计" 后的数字

    // 2. 从任务书提取每章分值
    chapterScores := extractChapterScoresFromTaskBook(
        taskBookContent, chapterCount,
    )
    // 在每章的"对应评分项"区块中匹配 "(N分)" 或 "N分" 模式

    // 3. 计算每章字数
    wordCounts := make(map[int]int)
    for chapterNum, score := range chapterScores {
        wordCounts[chapterNum] = totalWordCount * score / totalScore
    }

    return wordCounts, totalScore, nil
}
```

**评分分值提取正则：**

```go
// 总分提取 — 匹配 "总分：30 分" 或 "总分 30 分" 或 "合计 30分"
var totalScoreRe = regexp.MustCompile(`(?:总分|合计|满分)[：:]\s*(\d+)\s*分?`)

// 每章分值 — 匹配 "设计方案 (2分)" 或 "质量管理体系 2分"
var itemScoreRe = regexp.MustCompile(`\((\d+)\s*分\)`)
```

**优先级：**
1. 如果能成功提取总分和各章分值 → 精确分配
2. 如果提取失败 → 均分（总字数 / 章数），并在 warnings 中提示
3. 如果总分也提取不到 → 默认总字数 50000 字（biaoshu-writer 技能典型值）

```typescript
export function createManualChapterArtifact(
  chapterNumber: number,
  chapterTitle: string,
  filePath: string,
): BiaoshuArtifactRecord {
  return {
    id: `chapter-${chapterNumber}`,
    name: `第${toChineseNumber(chapterNumber)}章：${chapterTitle}`,
    kind: 'BID_CHAPTERS',
    version: '-',
    status: 'valid',
    owner: 'AI写作',
    updatedAt: new Date().toLocaleString('zh-CN', { hour12: false }),
    storageRef: filePath,
    summary: '并发生成的章节初稿',
    sourceTool: 'chapter_generation',
    metadata: { chapterNumber },
  }
}

// 章节输出目录推导
export function deriveChapterOutputDir(outlinePath: string): string {
  const dir = path.dirname(outlinePath)
  return path.join(dir, '章节')
}
```

```typescript
function toChineseNumber(n: number): string {
  const digits = ['', '一', '二', '三', '四', '五', '六', '七', '八', '九']
  const tens = ['', '', '二十', '三十', '四十', '五十', '六十', '七十', '八十', '九十']
  if (n <= 0) return '零'
  if (n <= 10) return ['', '一', '二', '三', '四', '五', '六', '七', '八', '九', '十'][n]
  const t = Math.floor(n / 10), d = n % 10
  return tens[t] + (d ? digits[d] : '')
}
```

## 5. 关注点与风险

### 5.1 Token 预算管理

| 组成部分 | 预估 tokens |
|----------|------------|
| System Prompt | ~800 |
| 任务书（截断 20000 runes） | ~10000 |
| 大纲章节（子集） | ~3000 |
| 评分标准（截断 8000 runes） | ~4000 |
| 项目背景（截断 8000 runes） | ~4000 |
| 解析报告（截断 8000 runes） | ~4000 |
| **合计 prompt** | **~26800** |
| max_tokens（输出） | 8000 |
| **总计** | **~34800** |

需确保所用模型上下文窗口 ≥ 64K（deepseek-v4-pro 满足）。

### 5.2 大纲解析可靠性

大纲格式依赖 `## 一、XXX` 的 markdown 模式。如果大纲格式差异较大，解析可能失败。需做以下防御：
- 正则匹配失败时，使用整个大纲作为单章处理
- 生成的章节数 ≤ 1 时返回明确错误

### 5.3 并发控制

同时 3 个 LLM 调用 + 每章 60-120s → 总耗时约 `ceil(N/3) × 120s`。对 6 章项目约需 4 分钟。

需设置足够超时：
- axios: 600s (10 分钟)
- OpenAI client: 300s (已是 300s，够用)

### 5.4 单章失败不阻塞

如果某一章 LLM 调用失败，其他章继续生成。失败章结果中 `error` 字段有错误信息，前端不应中断整体流程。
