# 下一步完整优化方案

## 0. 当前阶段判断

你现在不需要再大改架构。当前系统已经具备动态 Agent 主链路：

```text
LLM Planner / Heuristic Planner
  ↓
AgentPlan
  ↓
PlanGuard
  ↓
PlanCompiler
  ↓
Transient DAG
  ↓
Orchestrator / Worker
```

`LLMPlanner` 当前已经要求模型只输出 `AgentPlan JSON`，并明确禁止输出 `DAGRequest / workflow_template / ai_node`；同时它仍然使用启发式 `selectTools` 作为候选工具筛选，然后再调用 LLM 生成计划。([GitHub][1])

`PlanGuard` 现在已经有基础校验：空计划、步骤数量、工具存在性、成本、风险、必填参数、参数类型、引用表达式、`maxToolCalls` 等，并且会对缺少质量检查器给 warning。([GitHub][2])

`PlanCompiler` 已经开始支持 `QualityPolicy` 自动插入质量检查节点，并且能根据 `ApprovalPolicy` 自动插入审核节点。([GitHub][3])

核心视频 Prompt Tool 也已经加入动态工具列表，包括 `video_script_generator / shot_splitter / video_prompt_generator / quality_checker / video_package_exporter` 等。([GitHub][4])

所以，下一步重点不是“继续扩框架”，而是把系统从：

```text
动态 Agent 能跑
```

升级成：

```text
动态 Agent 稳定产出高质量完整视频创作包
```

# 3. P0：主链路稳定性优化

## 3.1 让 LLM Planner 真正走 ModelGateway

### 当前问题

`main.go` 中 Agent Planner 构建发生在 ModelGateway 初始化之前，并且当前传入的是：

```go
agentPlanner := buildAgentPlanner(cfg, toolRegistry, nil)
```

后面才初始化：

```go
gw := modelgateway.NewGateway(cfg.Video.ModelProviderMode)
```

这意味着动态 Agent 的 Planner 很可能没真正走 ModelGateway，而是走 OpenAIPlannerClient。([GitHub][5])

### 目标

统一所有 LLM 调用：

```text
LLMPlanner
PromptTool
JSONRepairer
QualityChecker
ArtifactRevision
```

都走：

```text
ModelGateway
```

### 改造方案

把 ModelGateway 初始化提前。

推荐结构：

```go
// 1. 先初始化 ModelGateway
var gw *modelgateway.Gateway
if cfg.Video.VideoCreationEnabled {
    gw = modelgateway.NewGateway(cfg.Video.ModelProviderMode)

    if cfg.Video.ModelProviderMode == "real" {
        openaiProvider := openai.NewProvider()
        gw.RegisterProvider(openaiProvider, modelgateway.CapTextToText)

        switch cfg.Video.ImageProvider {
        case "stability":
            gw.RegisterProvider(stability.NewProvider(), modelgateway.CapTextToImage)
        default:
            gw.RegisterProvider(openaiProvider, modelgateway.CapTextToImage)
        }
    } else {
        fakeProvider := fake.NewProvider()
        gw.RegisterProvider(fakeProvider, modelgateway.CapTextToText)
        gw.RegisterProvider(fakeProvider, modelgateway.CapTextToImage)
    }

    builtin.SetModelGateway(gw)
}

// 2. 再构造 Agent Planner
agentPlanner := buildAgentPlanner(cfg, toolRegistry, gw)
```

### 验收标准

```text
1. dynamic_agent planner_type=llm 时不再直接使用 OpenAIPlannerClient
2. fake provider 模式下 /api/agent/runs 可以跑通
3. 日志中能看到 planner 使用的 provider / model / latency
4. 本地用户自定义模型配置后，LLMPlanner 能使用该配置
```

## 3.2 把知识类工具改成强结构化 JSON

### 当前问题

`knowledge_researcher / fact_checker` 如果输出 Markdown，后续步骤引用：

```text
{{knowledge_research.output.facts}}
{{fact_check.output.checkedFacts}}
```

就不稳定。你现在已经对视频核心工具做了结构化 JSON，但知识类工具也必须同样结构化，否则知识视频的第一步就不稳定。`executeDynamicAgentPromptTool` 当前会调用 LLM 并尝试解析 JSON。([GitHub][4])

### 目标

`knowledge_researcher` 固定输出：

```json
{
  "facts": [],
  "timeline": [],
  "storyAngles": [],
  "risks": [],
  "sourceNotes": [],
  "summary": ""
}
```

`fact_checker` 固定输出：

```json
{
  "checkedFacts": [],
  "warnings": [],
  "corrections": [],
  "passed": true,
  "summary": ""
}
```

### Prompt 改造

`knowledge_researcher`：

```text
你是知识分享视频资料研究员。

任务：
根据 topic 整理适合短视频口播的事实材料、讲述角度、风险点。

要求：
1. 不要输出 Markdown。
2. 只输出 JSON。
3. 不要编造明确历史细节。
4. 对不确定内容写入 risks。
5. facts 应该短句化，适合后续口播稿生成。
6. storyAngles 给出 3-5 个短视频讲述角度。

输出 JSON：
{
  "facts": [],
  "timeline": [],
  "storyAngles": [],
  "risks": [],
  "sourceNotes": [],
  "summary": ""
}
```

`fact_checker`：

```text
你是知识类短视频事实核查员。

任务：
检查 facts 中是否存在不稳妥、过度简化、容易误导或需要谨慎表达的内容。

要求：
1. 不要输出 Markdown。
2. 只输出 JSON。
3. 保留稳妥事实到 checkedFacts。
4. 把不确定或争议内容写入 warnings。
5. 对需要改写的内容写入 corrections。

输出 JSON：
{
  "checkedFacts": [],
  "warnings": [],
  "corrections": [],
  "passed": true,
  "summary": ""
}
```

### 验收标准

```text
1. knowledge_researcher 输出 facts 字段
2. fact_checker 输出 checkedFacts 字段
3. video_script_generator 可以稳定引用 {{fact_check.output.checkedFacts}}
4. 如果知识类工具输出非 JSON，工具执行失败，而不是继续执行
```

## 3.3 完成 output schema 引用字段校验

### 当前问题

`PlanGuard` 已经检查了：

```text
{{step.output.field}}
```

中的 step 是否存在、是否在 dependsOn 中。([GitHub][2])

但当前还没有真正检查：

```text
field 是否存在于上游工具的 output schema
```

代码里 `refField` 仍然是 future output schema validation。([GitHub][2])

### 目标

如果 LLMPlanner 输出：

```json
{
  "facts": "{{knowledge_research.output.checkedFacts}}"
}
```

而 `knowledge_researcher.output` 没有 `checkedFacts`，Guard 必须拦截。

### 改造方案

把：

```go
func validateReferenceExpressions(step AgentStep, stepMap map[string]AgentStep) error
```

升级为：

```go
func validateReferenceExpressions(
    step AgentStep,
    stepMap map[string]AgentStep,
    stepManifests map[string]*tool.ToolManifest,
) error
```

核心逻辑：

```go
refStepID := matches[1]
refField := matches[2]

refStep, exists := stepMap[refStepID]
if !exists {
    return fmt.Errorf("step %s references unknown step %s", step.ID, refStepID)
}

refManifest := stepManifests[refStep.ID]
if refManifest == nil {
    return fmt.Errorf("step %s references step %s without manifest", step.ID, refStepID)
}

if _, ok := refManifest.Output[refField]; !ok {
    return fmt.Errorf(
        "step %s references output field %s of %s, but tool %s does not declare this output",
        step.ID, refField, refStepID, refStep.Tool,
    )
}
```

### 验收标准

```text
1. 引用不存在字段时 Guard 失败
2. 引用未 dependsOn 的 step 时 Guard 失败
3. 引用存在字段时 Guard 通过
```

# 4. P1：质量门与审核闭环

## 4.1 质量检查不通过时阻断下游

### 当前问题

`PlanCompiler` 已经能根据 `QualityPolicy.Required` 自动插入质量检查器。([GitHub][3])

但如果质量检查器输出：

```json
{
  "passed": false,
  "score": 62
}
```

下游可能仍然继续执行。

### 目标

质量检查结果必须控制执行流。

推荐规则：

| 分数 / 结果                    | 动作      |
| -------------------------- | ------- |
| `passed=true && score>=85` | 继续      |
| `score 70-84`              | 自动修复一次  |
| `score<70`                 | 暂停，用户确认 |
| `passed=false`             | 阻断下游    |
| JSON 格式错误                  | 工具失败    |

### 方案 A：新增 SYSTEM_GATE 节点

如果你愿意扩展节点类型，可新增：

```text
SYSTEM_GATE
```

编译后：

```text
video_script_generator_exec
  ↓
script_quality_checker_exec
  ↓
script_quality_gate SYSTEM_GATE
  ↓
script_review CONTROL
  ↓
shot_splitter_exec
```

`SYSTEM_GATE` 根据质量结果判断：

```go
if !passed || score < minScore {
    return GateBlocked
}
return GatePassed
```

### 方案 B：复用 CONTROL 节点

不新增节点类型，直接插入系统审核控制节点：

```text
script_quality_checker_exec
  ↓
script_quality_gate CONTROL
```

但这个 CONTROL 不是用户审核，而是系统质量门：

```json
{
  "reviewPhase": "quality_gate",
  "sourceNode": "script_quality_checker_exec",
  "minScore": 85,
  "autoApproveWhenPassed": true
}
```

质量通过时系统自动标记 SUCCESS；不通过时暂停或返工。

第一版建议用 **方案 B**，侵入更小。

### 验收标准

```text
1. quality_checker score < 85 时，下游节点不执行
2. score >= 85 时，下游继续
3. 不通过时可以在 AgentRun trace 看到阻断原因
```

## 4.2 自动修复一次

### 目标

质量分数在 70-84 时自动修复一次，不要每次都打断用户。

流程：

```text
生产工具输出
  ↓
质量检查
  ↓
score=78
  ↓
调用 revise 工具 / 原工具带 repairInstruction 重跑一次
  ↓
再次质量检查
  ↓
通过则继续，不通过则暂停
```

### 实现方式

在 `QualityPolicy` 增加：

```go
type QualityPolicy struct {
    Required          bool   `json:"required"`
    CheckerTool       string `json:"checkerTool"`
    MinScore          int    `json:"minScore"`
    AutoRepair        bool   `json:"autoRepair"`
    MaxRepairAttempts int    `json:"maxRepairAttempts"`
    RepairTool        string `json:"repairTool,omitempty"`
}
```

如果没有 `RepairTool`，用原工具重跑：

```json
{
  "repairInstruction": "{{script_quality_check.output.repairSuggestions}}",
  "previousOutput": "{{script_generation.output}}"
}
```

### 验收标准

```text
1. score 70-84 自动修复一次
2. 修复次数不超过 maxRepairAttempts
3. 修复后的产物有新 version
4. trace 中能看到 repair attempt
```

## 4.3 Artifact Review 真正落表

### 当前问题

现在审核更多是 CONTROL 节点审核。`PlanCompiler` 已经给 review node 增加了 `sourceNode / artifactKinds / requiresApprovedArtifacts` 这类信息。([GitHub][3])

但下一步需要做到 artifact 级别。

### 目标

每个关键中间产物都有明确状态：

```text
PENDING
APPROVED
REJECTED
REVISED
```

### 表结构

```sql
CREATE TABLE IF NOT EXISTS artifact_reviews (
    id VARCHAR PRIMARY KEY,
    task_id VARCHAR NOT NULL,
    node_id VARCHAR NOT NULL,
    agent_run_id VARCHAR,
    artifact_id VARCHAR,
    storage_ref TEXT,
    artifact_kind VARCHAR,
    artifact_name TEXT,
    status VARCHAR NOT NULL,
    review_reason TEXT,
    reviewer_id VARCHAR,
    review_comment TEXT,
    created_at TIMESTAMP DEFAULT NOW(),
    reviewed_at TIMESTAMP
);
```

### 执行流程

```text
TOOL 节点成功
  ↓
解析 output.artifacts
  ↓
写 artifacts 表
  ↓
如果 artifact.metadata.requiresReview=true
  ↓
写 artifact_reviews PENDING
  ↓
CONTROL 节点绑定 reviewId
  ↓
用户 approve
  ↓
artifact_reviews = APPROVED
  ↓
CONTROL node = SUCCESS
```

### 未审核产物禁止下游读取

在 Worker 执行前增加：

```text
resolve arguments
  ↓
发现引用 artifact
  ↓
如果 requiresReview=true 且 status != APPROVED
  ↓
拒绝执行
```

### 验收标准

```text
1. 口播稿生成后 artifact_reviews 有 PENDING
2. 用户 approve 后状态变 APPROVED
3. 未 APPROVED 的 artifact 不能被 shot_splitter 使用
4. reject 后下游不执行
```

# 5. P2：工具检索升级

## 5.1 从启发式 selectTools 升级为 HybridToolRetriever

### 当前问题

`LLMPlanner` 当前仍然复用 `HeuristicPlanner.selectTools` 做工具候选选择。([GitHub][1])

工具少时能用；工具多时会不稳定。

### 目标

新增：

```text
cloud-backend/internal/core/agentruntime/tool_retriever.go
```

接口：

```go
type ToolRetriever interface {
    Retrieve(ctx context.Context, req RetrieveRequest) ([]*tool.ToolManifest, error)
}

type RetrieveRequest struct {
    Query           string
    Domain          string
    Stage           string
    PreviousTools   []string
    MaxCostLevel    string
    MaxRiskLevel    string
    CoarseTopK      int
    PlannerTopK     int
}
```

### 第一版混合检索

```text
1. Hard filter
2. Capability / tag / keyword recall
3. nextRecommendedTools boost
4. cost / risk penalty
5. topK rerank
```

评分：

```text
score =
  capability_score * 0.30
+ keyword_score * 0.25
+ tag_score * 0.20
+ next_tool_score * 0.10
+ domain_score * 0.15
- cost_penalty
- risk_penalty
```

### 第二版再接向量库

当工具超过 50 个后，再把以下内容做 embedding：

```text
name
description
capabilities
tags
whenToUse
whenNotToUse
examples
input/output schema summary
```

然后：

```text
Vector Top 30
  +
Keyword/Capability recall
  ↓
Rerank
  ↓
Planner Top 8
```

### 验收标准

端午节输入应返回：

```text
knowledge_researcher
fact_checker
video_script_generator
shot_splitter
video_prompt_generator
```

# 9. 端到端测试方案

## 9.1 核心 E2E

输入：

```text
请帮我根据端午节的来历创作一个口播知识分享视频。
```

断言：

```text
1. POST /api/agent/runs 成功
2. AgentPlan.steps 包含：
   - knowledge_researcher
   - fact_checker
   - video_script_generator
   - shot_splitter
   - video_prompt_generator
   - video_package_exporter

3. PlanGuard 通过
4. Compiler 生成 transient DAG
5. DAG 中有质量检查节点
6. DAG 中有 CONTROL 审核节点
7. knowledge_researcher 输出 JSON.facts
8. fact_checker 输出 JSON.checkedFacts
9. video_script_generator 输出 JSON.script
10. shot_splitter 输出 JSON.shotList
11. video_prompt_generator 输出 JSON.videoPrompts
12. 口播稿未 approve 前，shot_splitter 不执行
13. 质量 score < 85 时，下游阻断
14. 最终 package_manifest.json status 正确
```

## 9.2 Guard 单测

```text
1. unknown tool → fail
2. missing required param → fail
3. wrong param type → fail
4. unknown output field reference → fail
5. missing dependsOn for reference → fail
6. high risk above budget → fail
7. sideEffect without approval → fail
```

## 9.3 Compiler 单测

```text
1. after_artifact → TOOL → CONTROL
2. before_execute → CONTROL → TOOL
3. qualityPolicy.required → auto insert checker
4. quality checker output node becomes dependency of review/downstream
```

# 12. 最终建议

你下一步不要再扩更多 Agent，不要急着做多 Agent 通信，也不要马上上复杂向量数据库。

当前最重要的是把这条链路打磨稳定：

```text
自然语言
  ↓
LLMPlanner
  ↓
HybridToolRetriever
  ↓
AgentPlan
  ↓
PlanGuard
  ↓
PlanCompiler
  ↓
PromptTool
  ↓
QualityGate
  ↓
ArtifactReview
  ↓
PackageExporter
```

一句话：

> **先把单 Agent + 多工具 + 质量门 + 人审门 + 完整包导出做到稳定，再考虑多 Agent、向量库和自动发布。**
