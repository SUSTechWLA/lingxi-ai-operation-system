# Agent 系统用户注册登录完整解决方案

## 1. 当前目标

你现在不是要做完整企业级权限系统，而是先解决一个核心问题：

```text id="0418cl"
用户可以注册 / 登录
↓
服务端能够识别当前请求属于哪个用户
↓
所有工作流、模型配置、项目、日志都能绑定 user_id
↓
后续 ModelProfile、DeviceID、工作流运行记录都可以基于 user_id 隔离
```

第一版建议只做：

```text id="rdsa6h"
用户注册
用户登录
Token 鉴权
刷新 Token
退出登录
获取当前用户信息
请求上下文注入 user_id
```

暂时不要做：

```text id="hb7ev0"
复杂 RBAC
团队组织
OAuth 第三方登录
管理员后台
多租户审批
企业 SSO
```

---

# 2. 推荐总体架构

```text id="5r2bqo"
Electron / Web 前端
  ↓
Auth API
  ↓
User Service
  ↓
PostgreSQL
  ↓
Auth Middleware
  ↓
业务 API / Workflow API / ModelProfile API
  ↓
从 RequestContext 获取 user_id
```

最终效果是：

```text id="ufqyoh"
前端请求接口
  ↓ Header 携带 access_token
后端 AuthMiddleware 校验 token
  ↓
解析出 user_id
  ↓
写入 request context
  ↓
后续所有服务直接从 context 获取 user_id
```

---

# 3. 核心原则

## 3.1 不允许前端直接传 user_id

不要这样：

```http id="nyafcp"
POST /api/workflows/run
UserID: u_001
```

前端传来的 `user_id` 不可信。

应该这样：

```http id="712cz2"
POST /api/workflows/run
Authorization: Bearer access_token
DeviceID: device_xxx
```

后端从 `access_token` 中解析出：

```text id="9qlss8"
user_id = u_001
```

然后注入上下文。

---

## 3.2 user_id 是所有用户资源的主隔离字段

后续这些表都要绑定 `user_id`：

```text id="apbm9a"
model_profile.user_id
workflow_run.user_id
video_project.user_id
model_call_log.user_id
device.user_id
file_asset.user_id
```

这样才能保证：

```text id="4mh2ot"
用户 A 不能访问用户 B 的模型配置
用户 A 不能看到用户 B 的工作流
用户 A 不能调用用户 B 的 API Key
```

---

# 4. 登录方案选择

推荐第一版使用：

```text id="q6dl75"
邮箱 + 密码注册登录
Access Token + Refresh Token
```

原因：

```text id="j53mac"
1. 实现简单
2. Electron 和 Web 都能用
3. 后续容易扩展微信、GitHub、Google 登录
4. 后端可以稳定拿到 user_id
```

密码不能明文保存，应该使用专门的慢哈希算法。OWASP 建议密码不要明文存储，而应使用 Argon2id、bcrypt 或 PBKDF2 这类强、慢的密码哈希算法，并为每个密码使用唯一 salt；不应使用 SHA-256 这类快速哈希直接存密码。([cheatsheetseries.owasp.org][1])

# 5. Token 策略

## 5.1 Access Token

用途：

```text id="b8c5p6"
每次请求业务 API 时携带
```

特点：

```text id="dj41w9"
有效期短
通常 15 分钟 - 2 小时
不入库或只记录黑名单
```

Payload 示例：

```json id="1xgg9g"
{
  "sub": "u_001",
  "email": "test@example.com",
  "token_type": "access",
  "iat": 1760000000,
  "exp": 1760003600
}
```

其中：

```text id="epc36j"
sub = user_id
```

---

## 5.2 Refresh Token

用途：

```text id="39x9x2"
Access Token 过期后换取新的 Access Token
```

特点：

```text id="ney4uf"
有效期较长
需要入库
服务端保存 hash，不保存明文
支持撤销
支持轮换
```

有效期建议：

```text id="6ig8t8"
7 天 / 30 天
```

第一版可以用 30 天。

---

## 5.3 Token 存储建议

对于 Web 端，不建议把认证 token、session ID、JWT、refresh token 等敏感凭证放在 `localStorage` 或 `sessionStorage`，因为一旦出现 XSS，JavaScript 可以直接读取这些值；OWASP 更推荐使用带 `HttpOnly`、`Secure`、`SameSite` 属性的 cookie。([cheatsheetseries.owasp.org][2])

所以建议：

| 客户端      | Access Token         | Refresh Token                       |
| -------- | -------------------- | ----------------------------------- |
| Web      | 内存 / HttpOnly Cookie | HttpOnly + Secure + SameSite Cookie |
| Electron | 内存                   | 系统 Keychain / 安全存储                  |
| 调试阶段     | Authorization Header | Authorization Header / 本地安全存储       |

Electron 第一版可以先放本地安全存储，不要长期放普通明文配置文件。

# 6. 数据库设计

## 6.1 users 表

```sql id="34byav"
CREATE TABLE users (
    id                VARCHAR(64) PRIMARY KEY,
    email             VARCHAR(255) NOT NULL UNIQUE,
    password_hash     TEXT NOT NULL,

    nickname          VARCHAR(128),
    avatar_url        TEXT,

    status            VARCHAR(32) NOT NULL DEFAULT 'active',

    created_at        TIMESTAMP NOT NULL,
    updated_at        TIMESTAMP NOT NULL,
    last_login_at     TIMESTAMP
);
```

字段说明：

| 字段              | 说明                                |
| --------------- | --------------------------------- |
| `id`            | 用户 ID，例如 `u_xxx`                  |
| `email`         | 登录邮箱                              |
| `password_hash` | 密码哈希                              |
| `status`        | `active` / `disabled` / `deleted` |
| `last_login_at` | 最近登录时间                            |

---

## 6.2 refresh_tokens 表

```sql id="3w81b7"
CREATE TABLE refresh_tokens (
    id                  VARCHAR(64) PRIMARY KEY,
    user_id             VARCHAR(64) NOT NULL,

    token_hash           TEXT NOT NULL,
    device_id            VARCHAR(128),

    user_agent           TEXT,
    ip_address           VARCHAR(64),

    expires_at           TIMESTAMP NOT NULL,
    revoked_at           TIMESTAMP,
    replaced_by_token_id VARCHAR(64),

    created_at           TIMESTAMP NOT NULL,

    CONSTRAINT fk_refresh_user
        FOREIGN KEY (user_id) REFERENCES users(id)
);
```

说明：

| 字段                     | 说明                 |
| ---------------------- | ------------------ |
| `token_hash`           | Refresh Token 的哈希值 |
| `device_id`            | Electron 设备 ID     |
| `revoked_at`           | 退出登录或撤销时写入         |
| `replaced_by_token_id` | Token 轮换时记录新 token |

---

## 6.3 devices 表

你前面提到了 `DeviceID`，这里可以开始正规化。

```sql id="s0011a"
CREATE TABLE devices (
    id              VARCHAR(128) PRIMARY KEY,
    user_id         VARCHAR(64) NOT NULL,

    device_name     VARCHAR(128),
    device_type     VARCHAR(64),
    platform        VARCHAR(64),

    last_seen_at    TIMESTAMP,
    created_at      TIMESTAMP NOT NULL,
    updated_at      TIMESTAMP NOT NULL,

    CONSTRAINT fk_device_user
        FOREIGN KEY (user_id) REFERENCES users(id)
);
```

作用：

```text id="cv5yaa"
1. 记录哪个设备登录过
2. 工作流请求可记录来源设备
3. 后续支持设备级配置
4. 后续支持踢下线
```

# 7. API 设计

## 7.1 注册

```http id="2ti03e"
POST /api/auth/register
Content-Type: application/json
```

请求：

```json id="2b0ppe"
{
  "email": "test@example.com",
  "password": "Password123456",
  "nickname": "Amos"
}
```

处理流程：

```text id="rr54us"
1. 校验 email 格式
2. 校验密码强度
3. 检查 email 是否已注册
4. 使用 Argon2id 或 bcrypt 生成 password_hash
5. 创建 users 记录
6. 创建 refresh_token
7. 返回 access_token 和 refresh_token
```

返回：

```json id="4f987v"
{
  "user": {
    "id": "u_001",
    "email": "test@example.com",
    "nickname": "Amos"
  },
  "access_token": "xxx",
  "refresh_token": "yyy",
  "expires_in": 3600
}
```

---

## 7.2 登录

```http id="7tc2o2"
POST /api/auth/login
Content-Type: application/json
DeviceID: device_xxx
```

请求：

```json id="914aln"
{
  "email": "test@example.com",
  "password": "Password123456"
}
```

处理流程：

```text id="syjon7"
1. 根据 email 查询用户
2. 用户不存在，返回统一错误
3. 校验 password_hash
4. 检查用户状态
5. 生成 access_token
6. 生成 refresh_token
7. refresh_token 哈希后入库
8. 绑定 device_id
9. 更新 last_login_at
10. 返回 token
```

返回：

```json id="d8zyfr"
{
  "user": {
    "id": "u_001",
    "email": "test@example.com",
    "nickname": "Amos"
  },
  "access_token": "xxx",
  "refresh_token": "yyy",
  "expires_in": 3600
}
```

---

## 7.3 刷新 Token

```http id="ofe30q"
POST /api/auth/refresh
Content-Type: application/json
```

请求：

```json id="pfy85u"
{
  "refresh_token": "yyy"
}
```

处理流程：

```text id="h7b70b"
1. 对 refresh_token 做 hash
2. 查询 refresh_tokens 表
3. 检查是否存在
4. 检查是否过期
5. 检查是否 revoked
6. 生成新的 access_token
7. 可选：轮换 refresh_token
8. 返回新 token
```

推荐开启 refresh token 轮换：

```text id="axifb9"
旧 refresh_token 立即失效
生成新的 refresh_token
replaced_by_token_id 指向新 token
```

---

## 7.4 退出登录

```http id="jz1ro5"
POST /api/auth/logout
Authorization: Bearer access_token
```

请求：

```json id="8x7p3k"
{
  "refresh_token": "yyy"
}
```

处理流程：

```text id="ib5okt"
1. 校验当前 access_token
2. hash refresh_token
3. 找到 refresh_tokens 记录
4. 确认属于当前 user_id
5. 设置 revoked_at
```

---

## 7.5 获取当前用户

```http id="ksrzxd"
GET /api/auth/me
Authorization: Bearer access_token
```

返回：

```json id="0nwsm8"
{
  "id": "u_001",
  "email": "test@example.com",
  "nickname": "Amos",
  "status": "active"
}
```

这个接口用于前端启动后判断登录态。

# 8. Auth Middleware 设计

所有需要登录的接口都经过中间件。

## 8.1 请求格式

```http id="ts5bhi"
Authorization: Bearer access_token
DeviceID: device_xxx
```

## 8.2 中间件处理流程

```text id="cx1kff"
1. 读取 Authorization Header
2. 校验 Bearer Token 格式
3. 验证 JWT 签名
4. 验证 exp 是否过期
5. 验证 token_type 是否为 access
6. 解析 sub 为 user_id
7. 查询用户状态是否 active
8. 将 user_id 写入 RequestContext
9. 将 device_id 写入 RequestContext
10. 放行请求
```

## 8.3 RequestContext

后续服务里统一这样拿：

```go id="2dyshr"
userID := authctx.GetUserID(ctx)
deviceID := authctx.GetDeviceID(ctx)
```

不要在业务层重新解析 token。

# 15. 第一版验收标准

## 15.1 注册登录验收

| 项目     | 标准                     |
| ------ | ---------------------- |
| 注册     | 新邮箱可以注册                |
| 重复注册   | 同邮箱不能重复注册              |
| 密码保存   | 数据库不能看到明文密码            |
| 登录     | 正确邮箱密码可以登录             |
| 错误密码   | 返回登录失败                 |
| 禁用用户   | 不能登录                   |
| 获取当前用户 | `/api/auth/me` 能返回当前用户 |

---

## 15.2 Token 验收

| 项目            | 标准                   |
| ------------- | -------------------- |
| 无 Token       | 访问业务接口返回 401         |
| 错 Token       | 返回 401               |
| 过期 Token      | 返回 401               |
| 正确 Token      | 可以访问业务接口             |
| Refresh Token | 可以刷新 Access Token    |
| Logout        | 退出后 Refresh Token 失效 |

---

## 15.3 业务隔离验收

| 项目          | 标准                          |
| ----------- | --------------------------- |
| 用户 A 创建模型配置 | `model_profile.user_id = A` |
| 用户 B 查询配置   | 查不到 A 的配置                   |
| 用户 A 创建工作流  | `workflow_run.user_id = A`  |
| 用户 B 查询工作流  | 查不到 A 的工作流                  |
| 模型调用日志      | 记录正确 user_id                |

---

# 16. 推荐最终架构文本

你可以把当前系统改造目标写成这样：

```text id="cbqc69"
系统新增用户认证模块，支持用户通过邮箱密码完成注册、登录、刷新 Token、退出登录和获取当前用户信息。用户密码使用安全哈希算法保存，Refresh Token 仅保存哈希值，Access Token 用于业务接口鉴权。

所有业务接口统一接入 AuthMiddleware。中间件负责解析 Authorization Header，校验 Access Token，获取 user_id，并写入请求上下文。业务层不接受前端传入 user_id，而是统一从 RequestContext 获取当前用户身份。

模型配置、视频项目、工作流运行记录、模型调用日志和设备信息均绑定 user_id。用户创建自定义 ModelProfile 时，服务端自动写入当前 user_id；工作流执行时，WorkflowContext 携带 user_id、device_id、model_policy 和 model_profile_id；ModelGateway 调用模型前基于 user_id 校验模型配置归属，保证用户数据隔离。

第一版仅实现单用户账号体系，不实现组织、角色、审批和第三方登录。后续如需支持团队协作，可在现有 user_id 基础上增加 workspace_id、member、role 和 permission 表。
```

---

# 17. 最终建议

你的开发顺序应该是：

```text id="zkk6o6"
用户注册登录
↓
AuthMiddleware 注入 user_id
↓
业务表补 user_id
↓
ModelProfile 绑定 user_id
↓
WorkflowRun 绑定 user_id
↓
ModelGateway 根据 user_id 校验配置
↓
DeviceID 作为来源记录接入
```

这样你后面的自定义模型 API、视频项目、Agent 工作流、日志审计都会有清晰的用户边界。
